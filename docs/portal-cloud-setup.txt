Application
- Supabase Auth: email/password, confirmed email, password recovery, PKCE.
- Allowed emails live in spatial_portal_members, editable only by an administrator.
  Initial allowed address: hub@groupmf.com.br. This does not create an Auth account.
- Documents belong to auth.uid(); RLS also requires enabled membership.
- Studio projects, budgets and lot operations have individual IDs. Existing main
  documents remain available in the library; new drafts and copies get new IDs.
- Operations copy a saved budget revision's commercial scope, without internal
  costs. Later budget edits do not change that snapshot. An operation with
  execution or receipts cannot be replaced by another proposal. Copying a plan
  resets receipts, approvals, spending, progress, activation and cancellation.
- New budgets model initial costs by four stages and 24 navigation-cloud months
  from the estimated launch. The analysis horizon is not the service term; future
  production/cloud costs outside it are disclosed. Legacy budgets retain their
  original timing until the owner explicitly enables stage planning.
- Management, briefings and production request lists are versioned documents.
- RPC saves use expected versions. Stale clients cannot overwrite newer versions.
- Private media: immutable originals, owner-prefixed paths, maximum 50 MB/file.
  Previews load on demand. Approval is versioned metadata; no public media URL.
- All local drafts remain untouched; import is explicit after sign-in and skips
  existing cloud documents. Media migration is a separate explicit action.
- JSON backup/restore includes documents; restore preserves existing documents.
  Media binaries use Production visual > Exportar biblioteca / Importar pacote.
- New portal data is not written into localStorage; only the Auth session persists.
  Public 3D experience preferences and MF rendering remain separate local features.

Required activation steps
1. Resolve project placement/cost. Inspect target tables AND storage.objects RLS
   policies before migration. If sharing a project, existing permissive storage
   policies must not expose this bucket; investigate before activation.
2. Both spatial_portal migrations above have been applied.
   It uses distinct spatial_portal_* names and does not modify EME Select tables.
3. Configure Auth:
   - Email provider enabled; Confirm email ON (already confirmed by public settings).
     The Spatial form requires a new password of at least 12 characters. Review
     global password policy without disrupting existing Select accounts.
   - Preserve the current Select Site URL in this shared project.
   - Add https://www.emespatial.com/portal to the redirect allowlist (and explicit preview URLs
     only while testing). Preserve all existing Select URLs.
   - Check existing SMTP; preserve it if it already supports production mail.
     Otherwise configure custom SMTP for confirmation/recovery to the business address.
     Built-in SMTP only delivers to organization team emails and is not production
     email infrastructure. Do not bypass this by disabling email confirmation.
   - Credentials entered directly by the owner in the service's secure UI; no
     passwords or service-role keys in this repository or conversation.
   - Review signup abuse protection/rate limits for the chosen mail provider.
4. Add Vercel build variables, with values from the selected Supabase project:
   VITE_SPATIAL_SUPABASE_URL=https://<project-ref>.supabase.co
   VITE_SPATIAL_SUPABASE_PUBLISHABLE_KEY=<publishable key>
   Never put a service_role key, secret key, database password or SMTP password
   in any VITE_ variable. Missing configuration intentionally closes the portal.
5. Run Supabase security/performance advisors. Verify actual remote RLS and
   private bucket behavior with permitted users and anonymous requests.
6. Deploy to preview, then the owner creates/confirms the first account directly.
   Check login, recovery, save/reload from a second browser, stale-write handling,
   logout, import preservation and binary media retrieval against the live service.
7. Publish production only after real configuration and those checks pass.
   Do not publish an unconfigured login gate over the currently working portal.
